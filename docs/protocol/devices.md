# Devices: the signed device roster

The account's devices, as a log of entries each signed by a device already in it (#55). The
design, its reasons and its proofs are in
`docs/design/device-approval.md` (PR #391, not yet merged); this file is the
wire contract implementations share. It is not [roster.md](roster.md), the relay's list of
machines seen online.

**Status: R1a, R1b and R1c.** R1a is the encoding: framing, ids, entries, their strict parsing,
presence assertions and the values enrollment computes. R1b is the acceptance rule and state in C#
(design §3.3 to §3.5). R1c ports the rule to the PWA and adds vetoes, person commands and head
attestations in both. R1d keeps signing keys (TPM, DPAPI, WebCrypto). It is a library only: nothing in the host, the relay or a client uses it yet
(slices R2 to R5).

| Implementation | Where |
|---|---|
| C# (host, relay, app) | `src/AgentBridge.Roster`, tests in `tests/AgentBridge.Roster.Tests` |
| JavaScript (PWA) | `pwa/js/roster`, replaying the vectors in `pwa/test/unit/roster-vectors.test.mjs`, `roster-state.test.mjs` and `roster-commands.test.mjs` |
| Swift (iOS) | Not yet: left to slice A1, which replays the same vectors |

All three must accept and refuse the same inputs **with the same refusal code**, which is why the
checks below run in a fixed order. [vectors/roster.json](vectors/roster.json) is generated by
the C# tests (`UPDATE_PROTOCOL_VECTORS=1` rewrites it) and replayed by every other
implementation.

## Framing

Every hash, MAC and signature input is `F(x₁, …, xₙ) = L(x₁) ‖ … ‖ L(xₙ)`, where `L(x)` is the
length of `x` in bytes as a 4-byte big-endian unsigned integer, followed by `x`. Labels are their
ASCII bytes, the account id and roles their UTF-8 bytes, and hashes, nonces and keys their raw
bytes.

| Label | Used for |
|---|---|
| `agent-bridge roster entry v1` | `sig`: `by`'s signature over `F(label, bodyBytes)` |
| `agent-bridge roster cosign v1` | `cosig`: the cosigner's signature over `F(label, bodyBytes)` |
| `agent-bridge presence v1` | A presence assertion's challenge: `SHA-256(F(label, role, bodyBytes))`, `role` being `by` or `cosigner` for an entry, `veto` for a veto and `command` for a person command |
| `agent-bridge enroll commit v1` | `C = SHA-256(F(label, h, nN))` |
| `agent-bridge enroll v1` | `T = SHA-256(F(label, account, h, nA, nN))` |
| `agent-bridge enroll code1 v1`, `… code2 v1` | `codeN = U32(SHA-256(F(label, T))) mod 10⁶`, six digits, zero-padded |
| `agent-bridge enroll key v1` | What a joining person's device signs with `sign`: `F(label, h)` |
| `agent-bridge invite hint v1` | `hex(HMAC-SHA256(q, F(label))[0..7])` |
| `agent-bridge enroll qr joiner v1`, `… qr approver v1` | `HMAC-SHA256(q, F(label, h))` |
| `agent-bridge roster head v1` | A head attestation's MAC input (below) |
| `agent-bridge person command v1` | What a person command's `by` signs: `F(label, bodyBytes)` |
| `agent-bridge reset veto v1` | What a veto's `by` signs: `F(label, bodyBytes)` |

## Encodings

* **Binary values** are base64url **without padding**, in their one canonical spelling: no `=`,
  nothing outside `A–Z a–z 0–9 - _`, no length that leaves one character over, and zero unused
  trailing bits. Anything else is `base64`. A value of the wrong decoded length is `length`.
* **Device ids and generations** are exactly 32 lowercase hex characters (`id`). A device id is
  `hex(SHA-256(dh)[0..15])`.
* **Public keys** (`dh`, `sign`, a WebAuthn credential's `key`) are uncompressed SEC1 P-256 points
  (`0x04 ‖ X ‖ Y`, 65 bytes), with X and Y below p and on the curve (`point`). Implementations check
  this with their own arithmetic, not a platform import, so every platform agrees.
* **Roster signatures** (`sig`, `cosig`) are strict minimal DER `SEQUENCE { INTEGER r, INTEGER s }`
  with short-form lengths, no needless leading zero, nothing after, r and s in `[1, n)` (`der`),
  and `s ≤ n/2` (`high-s`). A signer converts WebCrypto's or CryptoKit's raw `r ‖ s` and
  normalizes to low-S. **An assertion's signature** (`uv`) follows the same rule, so nobody without
  the key can flip (r, s) to (r, n − s) and push an entry at its size limit over it; a client
  normalizes the signature an authenticator returns before it sends the assertion.
* **Entry hash**: `SHA-256(bodyBytes)`, written in base64url. **Head order** is ascending by the
  raw 32 bytes, compared byte by byte. The **genesis fingerprint** is the first 8 bytes of the
  genesis hash as lowercase hex in four groups of four (`7d0f 3a2e 1c4b 4d5e`).

## Entries

```json
{"body":"eyJ2IjoxLC…","sig":"MEUCIQ…","cosig":"MEQCIF…","uv":{"by":{…},"cosigner":{…}}}
```

The wrapper has `body` and `sig`, and optionally `cosig` and `uv`. `uv` has `by` and/or
`cosigner`; each is `{ authenticatorData, clientDataJSON, signature }`, all base64url. Every
sender and forwarder emits it **canonically**: members in that order, no insignificant
whitespace. A receiver accepts a wrapper with whitespace and forwards it canonically.

**Size** is measured over fixed content: the body bytes, the decoded signatures, and each
assertion's decoded parts. A `remove` is at most **46 KiB** (47,104 bytes); any other entry at most
**8 KiB** (8,192). Over either is `size`, on every path.

The body is UTF-8 JSON whose bytes are signed as they are; nobody re-serializes it. Its fields
and what they mean are design §3.2. Exactly these members, per `op`:

| `op` | Members besides `v`, `op`, `account`, `generation`, `seq`, `by`, `at` |
|---|---|
| `genesis` | `device` (a person's), `approval` `{ "method": "genesis" }` |
| `add` | `prev` (1), `device`, `approval` |
| `remove` | `prev` (1), `target`, `keep` (0 to 512), optional `cosigner` |
| `rename` | `prev` (1), `target`, `name` |
| `confirm` | `prev` (1), `target` |
| `merge` | `prev` (2 to 4), optional `adopt` (only `true`) |

A device has `id`, `dh`, `kind` (`host`, `app`, `pwa` or `phone`; never `test`), `platform`
(`windows`, `macos`, `linux`, `ios`, `ipados` or `android`) and `name`. A person's device (any
kind but `host`) also has `sign`, `signAlg` (`p256-sha256-der`) and `presence` (`key`,
`webauthn` or `none`), plus `webauthn` `{ rpId, credentialId, key, attested, backupEligible }`
exactly when `presence` is `webauthn`. `approval` is exactly one of `{ method: "code",
transcript }`, `{ method: "qr", transcript, shown: "approver" | "joiner" }`,
`{ method: "grandfather" }`, or, on a genesis only, `{ method: "genesis" }`. A transcript is
32 bytes. `target` is `{ id, add }`, `add` being an entry hash.

### Strict parsing, in order

The input is I-JSON (RFC 7493): valid UTF-8, no byte-order mark, valid JSON, at most 16 levels of
arrays and objects, no lone surrogate in any string or name (`json`), and no two members of one
object with the same name after unescaping (`duplicate-member`). The syntax is checked over the
whole input first; then each member in document order: its name, whether it repeats one, and
then its value. Names and enumerated values are case-sensitive.

**The wrapper:** an object (`type`); no member but the four (`unknown-member`); `body`, then
`sig`, present (`missing-member`); `body`'s base64url; `sig`'s, then its DER and low-S; the same
for `cosig`; `uv` an object with only `by` and `cosigner`, and not empty (`value`), each assertion
with exactly its three members and minimal DER. Then the size against 46 KiB; then the body;
then the size against 8 KiB unless it is a `remove`. Last, `cosig` is present exactly when
the body has `cosigner`, and `uv.cosigner` only when it does (`cosigner`).

**The body:** an object; `v` present (`missing-member`), and exactly the number `1`
(`version`); `op` present, a string (`type`) and one of the six (`value`). Then any member its op
does not allow (`unknown-member`, the first in document order), then the first missing one, in
the order `v op account generation seq prev by cosigner at device approval target keep name
adopt`. Then each field in that same order:

| Field | Refused when, with code |
|---|---|
| `account` | Not 1 to 128 UTF-8 bytes, or holding a control character (`account`) |
| `generation`, `by`, `cosigner`, ids | Not 32 lowercase hex (`id`) |
| `seq` | Not plain decimal digits below 2³¹, or not 0 exactly on a genesis (`seq`). A leading zero is not JSON (`json`) |
| `prev`, `keep` | Not an array (`type`); the wrong number of hashes (`count`); a hash not base64url (`base64`) or not 32 bytes (`length`); not strictly ascending in head order (`order`) |
| `at` | Not `YYYY-MM-DDTHH:MM:SS` with up to nine fraction digits and `Z`, on a real calendar date (`time`) |
| `device` | In the order `kind` (missing, then a known kind: `value`), `presence` for a person's device (missing, then `value`), its members (`unknown-member`, then `missing-member` in the order `id dh sign signAlg presence webauthn kind platform name`), `id`, `dh`, `id` being `dh`'s (`device`), `sign`, `signAlg` (`value`), `webauthn`, `platform` (`value`), `name` |
| `webauthn` | Its five members; `rpId` a lowercase DNS name of at most 253 characters (`value`); `credentialId` 1 to 1,023 bytes (`length`); `key` a point; `attested` and `backupEligible` booleans (`type`) |
| `approval` | Anything wrong in it at all (`approval`) |
| `target` | Exactly `id` and `add`; `add` 32 bytes |
| `name`, `device.name` | Empty, over 64 Unicode scalars or 256 UTF-8 bytes, or holding a C0 or C1 control or DEL (`name`). Any other hidden character is kept, and a client shows it escaped |
| `adopt` | Not a boolean (`type`); `false` (`value`) |

Last, what the body alone says of its signers: a genesis adds a person's device (`device`) and
is signed by it (`signer`); a removal of its own signer keeps nothing and has no cosigner
(`signer`); a cosigner is neither the signer nor the target (`signer`).

A string where another type belongs, or the reverse, is `type`. Whether an entry is valid where
it is (its parents, its signer's standing, its signatures) is the acceptance rule's to say, not
the parser's.

## Presence assertions

A signer whose `presence` is `webauthn` proves presence with an assertion under the credential
recorded in its add, over the challenge `SHA-256(F("agent-bridge presence v1", role, bodyBytes))`.
A verifier checks it against that credential alone, never against a list of platforms, in this
order:

1. `authenticatorData` is exactly 37 bytes, with the attested-credential-data and extension flags
   clear (`uv-authenticator-data`).
2. Its first 32 bytes are `SHA-256(rpId)` (`uv-rp-id`).
3. User present and user verified are set, and backed-up is not set without backup-eligible
   (`uv-flags`).
4. Backup-eligible equals the recorded `backupEligible`, and a credential recorded as
   backup-eligible never proves presence in v1 (`uv-backup`).
5. `clientDataJSON` is strict JSON, as above, and an object (`uv-client-data`).
6. Its `type` is `webauthn.get` (`uv-type`).
7. Its `challenge` is the expected challenge in base64url (`uv-challenge`).
8. Its `origin` is `https://` + `rpId`, `crossOrigin` is absent or `false`, and there is no
   `topOrigin` (`uv-origin`).
9. `signature` verifies under the credential's key over `authenticatorData ‖
   SHA-256(clientDataJSON)` (`uv-signature`).

Other members of the client data are allowed, as WebAuthn allows them.

## Enrollment values

The code exchange (design §4.2) and the QR paths (§4.3) compute the framed values in the table
above. A code is shown as two groups of three digits. What a person types is accepted with spaces
dropped, only as exactly six ASCII digits, and compared without an early exit. The QR secret `q`
is 16 bytes.

### The exchange state machines (A4)

`EnrollmentApprover` and `EnrollmentJoiner` (`src/AgentBridge.Roster/EnrollmentExchange.cs`) carry
out design §4.2 with no I/O. The caller moves the messages over the Noise channel and passes in the
channel's handshake hash `h`; they do not open channels, talk to the relay or show anything.

| Step | Joiner | Approver |
|---|---|---|
| 1 | `Commit()` returns `C` (refused while joining is locked) | `OnCommit(C)` returns the offer `nA`; one commit per attempt |
| 3 | `OnOffer(nA)` returns the reveal `nN` and shows code 1 | `OnReveal(nN)` is false, and ends the attempt, unless it matches `C` |
| 5 | | `EnterCode1(typed)`; code 2 and the transcript to sign exist only after a match |
| 6 | `EnterCode2(typed)` | |
| 8 | `Accepts(newest, own, approverId)`: the newest entry of the roster it has already verified (§3.5) is an `add` by that approver of exactly this descriptor, `approval.method` `code`, carrying this exchange's `T`; only after code 2 matched | |

A typed code gives `Match`, `Wrong`, `Ended` (three wrong entries, or the 5 minutes ran out) or
`Locked`. Limits (§4.4) are counted by `EnrollmentLockout` on the device the person types on: three
wrong code-1 entries block that pending device for 15 minutes, and three wrong in an hour lock the
approver for 15 minutes; three ended attempts in an hour lock a joiner's joining for 15 minutes.
Neither the relay nor the other device can reset them. An expiry blocks no pending device at an
approver. A relay that ends both channels has two different `h`, so the codes it could read off one
leg do not match the other.

`EnrollmentLockout` holds its counts in memory only. A restart would forget them, so the host that
runs an exchange must persist and restore the counts and blocks, or the limits can be reset by
restarting. That persistence belongs to the host slice that runs enrollment over the pipe (R3 in the
design's §12 table); until then a caller that does not persist them does not meet §4.4.

Not here: the channel, the relay's `pending` list and its 8-pending and 20-attempts limits (R2),
the QR paths (§4.3), signing the `add`, and any screen.

## Acceptance and state

A verifier (`RosterVerifier`) holds one generation's accepted entries as a DAG and decides each
entry offered to it, in an order where every entry follows its parents. This is design §3.3 to
§3.5; the scenarios of §10 are its tests and [vectors/roster-state.json](vectors/roster-state.json)
its shared vectors. Each entry is judged in the **history state of its parents** alone (the
state of the entries that are its ancestors, quarantine ignored), so what a verifier decides
about it does not depend on what else it holds or on delivery order. The C# tests check both
properties on the order-independent scenarios (not the quarantine ones, which depend on what a verifier held when an entry
arrived): each of 12 random parent-first orders reaches the same state and the
same verdicts (commutativity, convergence), and a verifier holding only an entry's ancestors
judges it as one holding everything does (prefix reduction).

R1b covers §10's acceptance and state scenarios. Its relay, host and client scenarios (`roster.submit`,
frontiers and evidence across hosts, freshness, replay marks, client mode) are tested with the slices
that build them (R2 to R5), and its person-command, attestation and veto scenarios with R1c.

### Verdicts

| Verdict | Meaning |
|---|---|
| `accepted` | Applied (a probationary device's grants are applied and held, below) |
| `quarantined` | Kept and gossiped, not applied: outside the window, a fifth head, or descending from a quarantined entry |
| `duplicate` | Already held |
| `refused` | Refused with a code below. One refused only for `cap` or `budget` is kept aside (at most 2,048) in case a removal brings it as evidence; it is never applied |

### Checks, in order

The first that fails gives the code, so every implementation refuses with the same one. The
signer is the add that made `by` active in the parents' state; "confirmed" is in that state.

1. `account`, `generation`: the verifier's.
2. `parent`: every `prev` held; a first entry is a genesis. `genesis`: a second genesis.
3. `seq`: one more than the largest parent's (0 for the genesis).
4. A genesis then needs only its own `signature` and `presence`.
5. `signer`: `by` is active and a person's device. `signature`, then `presence`: a device whose
   presence is `key` carries no `uv`; `webauthn` carries an assertion that passes the checks
   above; `none` cannot sign. Then the same three for a `cosigner`.
6. By op:
   * `add`: `readded` (its id was added in its history), `active-cap` (64 active), `cap` (512 adds
     or 4,096 entries other than removals), `budget` (the signer's 64 adds).
   * `remove`: `target` (an ancestor add of that id, active); `seniority` (uncosigned, not a
     self-removal, and the signer's add is not an ancestor of the target's); `cosign` (both
     signers confirmed, and their approval lineages, cut at the target, disjoint); `keep` (each
     kept add an ancestor in the target's subtree, signed by the target or another kept add, and
     no copy: no other add of its id in the history); `signer` (a signer that is the target, or in
     its subtree and not kept, unless it is a self-removal); `budget` (64 removals). Removals are
     never refused for the generation's caps.
   * `rename`: `target`; `seniority` (the target is the signer's own add or junior to it);
     `budget` (8 renames of one add); `cap`.
   * `confirm`: `target`; `confirm` (the signer is confirmed, signed the target's add, and the
     target is not yet confirmed); `cap`; `budget` (64).
   * `merge`: `merge` (one of its two to four parents an ancestor of another); `cap`; `budget` (64).
7. An entry on a parent kept aside is refused `evidence`. A removal on such ancestors admits them
   as evidence only if it is not a self-removal, each is signed by the target or a device of its
   subtree the removal does not keep, at most 256 come from each signer at this verifier and
   1,024 in all; otherwise it is refused `evidence`.

### Quarantine

An entry other than a removal, merge or genesis is quarantined on arrival when more than **8**
unquarantined entries it does not descend from are held (the window), or when it would make more
than **4** heads. Quarantine is inherited by descendants. A merge with `adopt` adopts its
ancestors once its signer is not quarantined, which can let another adopting merge adopt in turn;
adoption is irrevocable, as is local adoption of a head by the person at the machine
(`Adopt`). A quarantined removal applies when it is valid in the state of its unquarantined
ancestors.

Known gap: when a concurrent branch is longer than the window, the final name of a device can
depend on delivery order; see [#1435](https://github.com/danswett/agent-bridge/issues/1435).

### State

The applied state is computed from the unquarantined entries and the quarantined removals that
apply, in the order of design §3.5: what each removal takes (its target, and the adds of the
target's subtree under it that it does not keep) and bars; the raw void chains; which removals
shield their descendants (rank, then the rules for yields and for revoking the other's signer);
the final void causes; for each id, its adds neither void nor revoked, where a senior signer's add
displaces a junior's and the displaced adds and what they granted are void; then the active, the
confirmed, the conflicted (several adds of one id, none winning) and the names (the latest
non-void rename, the smallest hash among concurrent ones).

**Probation** (§3.4): an add that is not the genesis and not confirmed is on probation for 72 hours
of the verifier's running time from when it first accepted it (an earlier time reported at
enrollment can be adopted). A device whose approval lineage passes through a device on probation,
or through a held device, is **held**: active, shown, and not **served**.

**Names**: a rename signed by a device on probation, or by a held device, is **pending** until that
hold ends; the device is shown by its previous name meanwhile, with the pending one beside it
(`Name`, `PendingName`). A device not yet trusted must not change how approvers see it, for
example by renaming itself to look like a device they already know. The hold applies even where
the name rules would catch a look-alike, as defence in depth (decided by A, Trust lead,
2026-11-04). A rename signed by a trusted device applies at once, whoever it names.

### Where a removal is signed

`RemovalParents.Choose` gives the parent a remover's client signs a `remove` on (§3.3): of the
unquarantined entries under every holder's last attested heads and the relay's head, the smallest
(fewest ancestors, then lowest hash) holding the target's add, the signers' adds, a cosigned
removal's confirms and the kept adds, with no grant of the target or its subtree under it other
than the kept adds and what they need. When every such entry has some, it takes the smallest and
names the grants it cannot void by position. When none is under every holder, it takes the one
with the fewest ancestors outside what they all hold, and names the holders that lack it.

## Vetoes, person commands and head attestations

Design §5.6, §7.2 and §6.3. A veto and a person command travel as `{ "body", "sig", "uv"? }`,
parsed strictly like an entry: no other wrapper member, `uv` holding only `by`'s assertion (an
empty one is `value`), fixed content at most 8 KiB (`size`). Each check returns `null` or one code,
in the order below; a parser refusal uses the entry codes above.

**Veto** (`Veto.Parse`, `Veto.Check`; `parseVeto`, `checkVeto`). `body` is exactly `{ v: 1, op:
"veto", account, generation, reset, by, at }`: `reset` 32 bytes, `at` as an entry's. `sig` is by
`by`'s `sign` key over `F("agent-bridge reset veto v1", bodyBytes)`, and a `webauthn` device's
assertion is over the challenge for role `veto`. Checked against the relay's copy of the current
generation and the reset it holds: `account`, `generation`, `reset` (another reset), `signer` (not
an active person's device there; probation does not matter), `signature`, `presence`.

**Person command** (`PersonCommand.Parse`, `PersonCommand.Check`; `parsePersonCommand`,
`checkPersonCommand`). `body` is `{ v: 1, action, request, by, target: { machine, … }, …,
issuedAt, expiresAt, heads }`, with exactly the members its action has:

| `action` | Body members besides the common ones | `target` members besides `machine` |
|---|---|---|
| `transfer` | `to` | `session` |
| `folder-trust-answer` | `choice`, `nonce` | `question` |
| `update` | `nonce` | none |
| `forget` | none | none |
| `attest` | `nonce` | none |

`request` and `session` are lowercase UUIDs; `machine`, `by` and `to` device ids; `question` 1 to
128 characters of `A–Z a–z 0–9 . _ : -`; `choice` 1 to 256 UTF-8 bytes with no control character;
`nonce` 32 bytes; `issuedAt` and `expiresAt` RFC 3339 UTC as `at`; `heads` 1 to 4 hashes in head
order. `sig` is over `F("agent-bridge person command v1", bodyBytes)`, the assertion for role
`command`. The library checks, in order: `action` (not the op's), `machine` (not this host),
`signer` (by is the machine or `to`, or is not an active person's device), `probation` (on
probation, or held), `signature`, `presence`, `lifetime` (expiring at or before issue, or over 10
minutes after), `future` (issued over 2 minutes after `now`), `expired` (expiring before `now`),
`floor` (issued at or before the floor), `nonce` (an action with one, not this channel's), `heads`
(a head the host does not hold: it syncs, then asks again), and for `attest` given the last
attestation's heads, `regress` (one of those is neither named nor an ancestor of one named).
Times compare exactly, to the nanosecond.

The library holds no state, so these are **the host's obligations** (R6, and R2 for freshness),
which no caller may skip:
* the **durable replay record**: `request` never used before, written and flushed before the
  action runs, kept until `expiresAt` plus 2 minutes has passed by the high-water mark;
* the **wall-clock high-water mark**, persisted, passed as `now` when it is later than the clock,
  with the **floor** a local clock reset sets, and the highest `issuedAt` accepted, persisted with
  the record;
* the **nonce** it gave the channel in `hello`, for an action that carries one;
* **freshness** (§6.3) before any action but `attest` under `selfAttest`, and the heads of the
  last attestation it took from another device, for `attest`.

**Head attestation** (`HeadAttestation`; `attestationKey`, `attestationMessage`, `attestationMac`,
`verifyAttestation`, `revokedAdds`). The key is a signed command's between the same two devices:
`HKDF-SHA256(ikm: ECDH(attester, host), salt: "agent-bridge command v1", info: "<attester id>|<host
id>")`. The MAC is `HMAC-SHA256(key, F("agent-bridge roster head v1", account, generation, heads,
host id, nonce, revoked))`, where `heads` and `revoked` are each one part, their 32-byte hashes in
head order joined, and `revoked` (the enrollment adds the host's applied state revokes, §6.3's
acknowledgement) is always there, empty when there are none. A signed command's MAC is over the
body's JSON bytes, and this input begins with its own label, so neither ever verifies as the
other. The library takes the raw ECDH secret, which the caller's key store computes.

## Signing keys

A person's device's `sign` key (design §3.2) is its own ECDSA P-256 key, beside its ECDH device
key, kept where it cannot be copied (#55 R1d). Every signature it makes is minimal DER with a low
S: the platforms sign in IEEE P1363 (`r ‖ s`), and S is replaced by n − S when it is the high one.

| Where | Store |
|---|---|
| Windows (the app) | `RosterSigningKeys` in `src/AgentBridge.Transport`: the TPM (Platform Crypto Provider, `ECDSA_P256`, per user, not exportable) when it can sign with P-256, else a software key encrypted to the user with DPAPI. A key never moves between them; a TPM key that cannot be opened means enrolling again. Forgetting the device deletes the TPM key itself |
| PWA | `pwa/js/roster/signing-key.js`: a WebCrypto key generated non-extractable, usable only to sign, kept in IndexedDB beside the device key |
| Apple clients | The Secure Enclave, with slice A1 |

`RosterSigningKeyTests` (in `tests/AgentBridge.Transport.Tests`) and
`pwa/test/unit/roster-signing-key.test.mjs` check the DPAPI and WebCrypto stores on every run. The
TPM test runs only on a machine whose TPM can sign with P-256. GitHub's runners have none, so after
a change here check it by hand on a Windows machine with a TPM 2.0:

```powershell
dotnet test tests/AgentBridge.Transport.Tests -c Release --filter "FullyQualifiedName~RosterSigningKeyTests"
# A_TPM_signing_key_… must pass, not be skipped. Then no test key may be left in the TPM:
certutil -user -csp "Microsoft Platform Crypto Provider" -key | Select-String agent-bridge-roster-sign
```
## The relay's copy

The relay keeps one append-only log per account and is an untrusted store (design §3.6): it keeps an entry only if the entry is valid against the relay's own copy, and a host verifies what it reads for itself and never takes the relay's word. Mode is `observe`: the relay serves every account's log and enforces nothing; no connection is refused for want of a roster entry.

Both messages are text frames from an admitted device of any kind, counted against the frame rate. Entries are the canonical text of §Framing. A device's own `id` (a number) is echoed so a reply can be matched.

```
-> {"t":"roster-get","id":1}
<- {"t":"roster","id":1,"mode":"observe","generation":"<hex>|null","entries":["<entry>",...]}

-> {"t":"roster-append","id":2,"entries":["<entry>",...]}
<- {"t":"roster-append-result","id":2,"results":[{"hash":"<b64url>","verdict":"accepted|quarantined|duplicate|refused","reason":"<code>|null"}]}
```

* One append carries 1 to 16 entries, offered in the order given (a parent before its child). Anything else is `{"error":"bad-request"}`; a store that could not be reached is `{"error":"unavailable"}` and nothing was kept.
* The first entry kept for an account must be a genesis whose `account` is the account's id; its `generation` then fixes the log. Any other first entry is refused `genesis`, a genesis for another account `account`.
* An entry that does not parse is refused with its parse code and an empty `hash`. Accepted and quarantined entries are kept; refused and duplicate ones are not.
* An entry over a signer's budget or a cap is refused for now. A later removal in the same append that needs it as evidence (§3.3) brings it in: it is kept, ahead of the removal, and its result becomes `accepted` with reason `evidence`. So send such ancestors and the removal in one append, parent first.
* `roster-get` is `{"error":"unavailable"}` too when the store cannot be reached. A stored log that does not decode or rebuild is never added to: an append says `unavailable`. So does an append that finds more than four others waiting on the account, and a request while the connection already has two roster requests running. Offering only entries already kept answers `duplicate` without replaying the log.
* The log is bounded at 224 KiB stored; an append that would pass it is refused `cap`.
* The relay judges time by its own clock. That is defence in depth: a host applies the same rules on its own clock.

## Pinned person devices

A read-only query over a verifier (`PinnedDevices.Query`), for #972 slice 2 and Daily's lists. It returns each person device the verifier serves (active, §3.5, and not held, §3.4; hosts are left out), in id order, as `id`, `name`, `kind`, `platform`, `presence`, `confirmed` and `quarantined`. `presence` is the declared level; only `key` and `webauthn` prove a person verified (§4.6), and `none` is listed so a client can say why a device cannot be offered. A Windows device stays `none` until R4 proves its mechanism. The query changes nothing and enforces nothing; the host verifier (OFF mode, next section) is what feeds it.

## The host's verifier (OFF mode)

A host reads the relay's copy with `roster-get` once after each connection and verifies it for itself, on its own clock: the generation is taken from the first genesis the relay holds for the account, every entry is offered to a `RosterVerifier`, and the host logs one line: entries read, how many were accepted, quarantined, refused or unreadable, and the head hashes (first 12 hex digits). It is `security.roster` = `off` (the only value this slice reads; anything else is reported in the log and read as `off`).

Off mode enforces nothing. No connection, command or approval is refused or changed because of what the roster holds or fails to hold, and a relay that does not answer, or answers with no roster, costs one log line. The roster reply is the one text frame the host reads past the ordinary frame bound (up to six times the relay's 224 KiB stored cap, for JSON escaping); a reply past even that is discarded as no roster, and the relay connection stays up (up to 4 MiB drained; beyond that, or for any other oversized text frame, the connection is closed as for any oversized frame). The generation is not pinned, so against a hostile relay this check protects nothing yet; observe and enforce modes, pinning and the ChannelHub gate are later slices.

## Vectors

[vectors/roster.json](vectors/roster.json) holds fixed test keys (`d`, `public`, `device`) and:

* `framing`, `base64url`, `points`, `der`, `ids`, `fingerprint`: the primitives.
* `signed`: what `sig` and `cosig` sign, and both presence challenges, for one body.
* `entries.valid`: a chain with every op, an entry at each size limit, and a whitespace-padded
  wrapper with its `canonical` form; each with its op, hash, size and signer, whose signatures
  and assertions verify.
* `entries.refused`: each changes one thing in a valid entry, with its `code`; a wrapper that is
  not valid UTF-8 is given as `wrapperHex`.
* `assertions`: presence assertions with the credential and challenge each is checked against,
  and the `code` of each that fails.
* `enrollment`: exchanges (the first has a code with a leading zero), typed codes, and QR MACs and
  invite hints.

[vectors/roster-state.json](vectors/roster-state.json) holds the acceptance rule's scenarios, each
with its `devices` (name to id), its `entries` (label, hash, wrapper) and its `steps`: an
`offer` of an entry with its `verdict` and refusal `reason`, `hours` that move the running-time
clock first (alone, they record who is `serving` then and the `names` shown), or an `adopt` of a head. Its `state` is
what the verifier then applies: the active devices with the add, confirmation and name shown of each (and a `pending` rename),
the conflicted ids, the heads, the quarantined entries, the evidence and who is served. A scenario with `limits` (`addCap`) runs a verifier with that
cap shrunk so it can be reached. Every refusal `reason` the verifier can give has a scenario that shows it. The PWA's
port (`pwa/js/roster/verifier.js`) replays it in `pwa/test/unit/roster-state.test.mjs`, with the same
verdicts, codes and state at every step (a scenario's `limits` shrink the port's cap the same way).

[vectors/roster-commands.json](vectors/roster-commands.json) holds a roster (its `entries`, every one
accepted at running time 0 and checked an hour later, so N is on probation), the `heldReset`,
and `vetoes` and `commands`, each a `wrapper` with the parser's `refusal` or the check's `code`
(`null`: taken), a command with the `context` it is checked in. Its `attestation` gives the two
devices' keys, the derived `key`, the `message` and `mac`, and a signed command's `body` and `mac`
under the same key, which must not verify the attestation. `RosterCommandTests.cs` writes it and
`pwa/test/unit/roster-commands.test.mjs` replays it.

## Decided for the library

Decided by A, Trust lead, 2026-11-04, where the design left them open:

| Question | Decision |
|---|---|
| How many entries refused for a cap or budget a verifier keeps aside as possible evidence | 2,048, twice the evidence it can admit; past that they are refused and dropped |
| Whether a held device's renames are held | Held: see **Names** above |
| What "distinct heads" means for a merge's parents | No parent an ancestor of another |
| §10's "partial cascade with a fabricated pair", whose bullet keeps E and E2 active | §3.5 governs, and the bullet is a design erratum (to be fixed after #391 lands): J's and K's removal also revokes D and E's add is not its ancestor, so E and E2 are void until enrolled again. A recovery of a device that approved others needs a cosigner, as the client asks |
| §10's removal that revokes only a fabricated duplicate of a device's id, whose bullet keeps the device's own add active | §3.5 governs: the removal never takes that add, so the device wipes nothing, but it bars it when the removal's signer was active where it was made, and the device then shows "not active". The bullet describes only the case without the bar (erratum #811) |
| What the library checks of a person command | Only what needs no state; the durable replay record, the high-water mark and floor, the nonce and freshness are the host's (R6, R2), named above |
| A person command's field formats | As above; `issuedAt` and `expiresAt` RFC 3339 UTC, as entries' times |
| The presence challenge roles for vetoes and person commands | `veto` and `command`, roles of their own, so an assertion made for one kind of signed object never stands for another |
| The head attestation MAC | The signed command's HKDF key, over an input that begins with `agent-bridge roster head v1`, so neither MAC verifies as the other; `revoked` is one more part after the nonce, always present (erratum #811) |
