# Beta feedback correlation contract, draft v1

This is a **proposal**, not an implemented protocol or approval to collect or upload
new data. [#1186](https://github.com/danswett/agent-bridge/issues/1186) tracks the
cross-team design; Engineering reviews the contract before implementation. The
sender, host, relay and inbox owners must resolve the open items below together.
The existing [sealed envelope](protocol/feedback-envelope.md) and
[feedback upload](protocol/feedback.md) remain authoritative until revised.

## Purpose and boundaries

When a tester sends feedback, authorized support needs to understand the relevant
host operation, relay upload, client and private feedback record. A correlation ID
is a pseudonymous join key, not proof of a person, device or operation. The existing
random envelope bundle ID identifies a report; it does not by itself trace an
operation through all components. Missing or unavailable links must be visible as
such, not inferred from timestamps or claimed to exist.

Manual feedback is separately initiated, previewed, sealed and sent to the private
inbox. Automatic diagnostics are a separate channel under #731, #732 and #741;
this contract does not enable them or change their notice, consent, regional,
security or retention gates. In particular, current builds remain default-off
until those gates are satisfied. If no automatic diagnostic was submitted, the
preview must not imply that one exists and the report must still send.

## Identifiers and trust

| Identifier | Scope and intended use | Trust and exposure |
| --- | --- | --- |
| Report / bundle ID | Fresh random 16-byte ID for a feedback bundle; the current envelope authenticates it in its header. | Client-generated. Authenticated by the envelope, but not proof of tester, machine or host operation. Private correlation only. |
| Operation request ID | The existing client-generated request UUID for a host action. A resend of the same request is the same attempt; a deliberate retry after `busy` or `refused` uses a new request. | A value in a client report is a claim, not proof that the host performed the operation. Only link actual events with matching IDs under their approved collection rules. |
| Upload reference | The relay generates a random 16-byte blob name per issuance; a new ticket uses a fresh name. The name alone is not the bearer credential. | Its safe transport, preview, binding and verification are **unresolved**. The bearer upload ticket or URL must not enter the bundle, preview, logs or issues. |
| Private record reference | The inbox's private report record and durable processing receipt. | Generated by the private processing path; never placed in a public issue as a join. |

New correlation IDs must not encode account, device, session, screen, content or
time and must not be derived from content or long-lived install IDs. A report may
refer to a particular attempt only when the tester can see and approve the relevant
information. The report ID, operation request ID and upload reference are different scopes: do not
reuse one as another, or join unrelated attempts merely because one report or
client contains them. Define exact encoding, bounds and version negotiation before
implementation; reject malformed or unknown versions rather than inventing a join.

An envelope authenticates its contents against tampering, not their truth. Even a
valid report can contain a forged attempt ID. If an inbox compares a decrypted
non-secret upload reference with an authenticated storage object's name, a match
can establish that the submitted claim matches that object's name; it does not
authenticate the device, account, host operation, sender or other claimed IDs.
Specify the trusted source, binding and failure handling before treating that match
as evidence of relay provenance.

## Proposed flow

1. The client sends the request UUID in the end-to-end encrypted host action. The
   answer result does not echo it: the response uses a separate numeric transport
   correlation. The relay cannot read the session protocol inside the Noise channel.
   The host's rotated local answer-attempt log currently records
   only the first eight hex characters, not the full UUID. That prefix can collide
   and is not sufficient proof of a unique join. The host's answer-attempt ledger
   also retains full request UUIDs for actions that reach its claim step, with
   30-day claim pruning and 15-minute outcome retention; it may contain session
   and question identifiers and is not an approved feedback attachment. A host
   record can be absent if the request never arrived or did not reach that step.
   The PWA keeps settled answer entries in memory until cleared and retains recent
   completed timing records in a bounded in-memory list. These records are not yet
   a feedback export or an approved support lookup. Connection proposes a bounded
   local per-attempt record, previewed and selected by the tester; its source,
   storage, lifetime and full-ID handling remain open. Do not invent a host or
   machine identity when the source cannot be authenticated.
2. The sender presents the **exact** content and correlation information to be
   sent, including which link is unavailable and whether an automatic diagnostic
   was actually submitted. Tester choice and preview apply independently of any
   automatic-diagnostics setting. For the #1132 automatic-event join, include
   its random per-attempt ID only when the corresponding event was actually
   recorded under the applicable decision and preview it.
3. The sender seals the approved report to the feedback public key. The relay
   remains write-only for feedback and receives no plaintext. It currently issues
   an exact-size, one-use bearer upload ticket **after** the sender has sealed the
   bundle; its HMAC ticket and URL are credentials, not report fields.
4. The inbox validates and decrypts the envelope, validates the report and any
   approved reference against its trusted storage context, and writes the private
   record idempotently. It records a durable receipt only after the required sink
   work succeeds. A missing, malformed, mismatched or unverified link must not
   become a successful cross-component join. If decryption succeeds, any retained
   report or quarantine must remain private; decryption or storage failure must
   be reported as unavailable, not represented as a readable report.
5. Authorized support can use the private lookup to navigate records that actually
   exist. Relay upload failures before a stored object exists cannot be represented
   as successful stored-blob links. Do not use account or device identity as a
   lookup key.

The sender/relay sequence above describes today's order, **not** a completed way
to include an upload reference in a sealed report. The current relay response
returns the URL and expiry, not a separate blob-name field; the name is embedded
within the bearer URL. Relay proposes obtaining a slot before sealing and using
the name alone, but Send Feedback and Relay must resolve how to expose it safely,
including exact preview, sizing, expiry and retries. Reusing the report ID across
fresh upload references also needs idempotent handling when a PUT succeeded but
its response was lost: the current private store is keyed by bundle name, not a
proven cross-upload report deduplication mechanism. The design must not leak the
bearer ticket, disclose plaintext to the relay, mutate tester-approved content
without renewed approval, or use a claimed reference as proof of identity. Until
the sequence and binding are reviewed, the upload reference is not an implemented
contract field.

## Private operations and retention

SRE owns an audited private operational lookup, restricted to named support roles,
joining approved random attempt and bundle IDs rather than account or device
identity. It contains neither raw feedback nor device identity. Define and verify
its actual source records, access enforcement, deletion and alerting before use;
an absent record is not proof that the operation failed.

The existing feedback container has a 30-day immutability hold and a day-31
lifecycle deletion. SRE proposes matching those defaults for the operational
lookup unless the owner approves otherwise. The private issue repository, receipts,
lookup, diagnostic events, exports and derived copies are separate stores: the
container policy does not enforce their retention or deletion. Each store needs
an explicit, verified retention and deletion mechanism before deployment; #741's
automatic events have their own approved retention. Alert on lookup or retention
failure without exposing report contents or identifiers in public alerts.

The relay currently logs outcomes and sizes only, never account, device or ticket.
Do not add an upload reference, ticket, attempt ID or other join key to relay logs
without an explicit relay, privacy and security review and approved retention.
Public issues remain deterministic and allowlisted: no cross-component attempt,
report or upload IDs or joins, tester text, raw logs, credentials or personal data.
The existing approved public grouping fingerprint is a separate purpose and must
not become a per-report or cross-component trace key. Private access and encryption
do not make free text anonymous; broader redaction is tracked separately in #1187.

## Required verification

Before enabling an implementation, use synthetic data to demonstrate an actual
host operation through the client, relay and inbox into the correct private record.
Prove each claimed join from its real source; if a component has no approved
record, show the missing link instead of treating the test as end-to-end success.
Include unavailable context and disabled diagnostics, report and upload retries,
concurrent unrelated attempts, malformed and forged IDs, mismatched references,
duplicate processing, ticket expiry and upload failure. Assert the exact preview
matches the sealed content and that credentials, correlation IDs, raw content and
personal data do not leak to public issues or prohibited logs. Verify access,
retention, deletion and alerting on the actual provisioned stores.

## Open decisions before implementation

- **Connection:** full request UUID versus truncated representation, local record
  lifetime, and trustworthy host/client evidence, including offline and retries.
- **Relay and Send Feedback:** non-secret upload reference, trusted binding,
  exact-size ticket acquisition, preview/seal/PUT ordering, ambiguous-success
  deduplication and retry behavior.
- **Send Feedback:** reviewed field schema, tester selection, exact preview and
  the behavior when context or diagnostics is missing.
- **SRE:** lookup schema, sources, support roles, audit, retention/deletion and
  alerts; how it joins only records that actually exist.
- **Engineering and privacy/security reviewers:** reconcile these sections with
  #732, #741 and the existing feedback protocol, then review the versioned schema,
  spoofing and leakage tests before any code or collection change.
